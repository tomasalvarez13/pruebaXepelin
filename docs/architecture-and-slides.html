Mini CRM para KAMs

Arquitectura, Stack y Decisiones de Producto
Prueba Técnica GE II — Part 1 Junio 2026

01Diagrama de Arquitectura

Frontend

Next.js 14 en Vercel con auth custom vía JWT almacenado en localStorage

Backend

NestJS con Passport JWT guard y señales determinísticas calculadas on-read

Datos

PostgreSQL en Railway con Prisma ORM, 4 tablas, indexes en (kamId) y (companyId, date)

02Stack Elegido

Capa Tecnología Por qué
Frontend Next.js 14 (App Router) Server components, file-based routing, deploy instant en Vercel. Estándar de mercado para dashboards React.
UI Mantine v7 + CSS custom Componentes accesibles out-of-the-box, customización vía CSS variables. Se complementó con CSS puro para el diseño premium (Stripe/Linear style).
Charts Recharts Librería React-native para gráficos, declarativa, liviana. Ideal para el AreaChart de volumen financiado.
Backend NestJS + TypeScript Framework opinado con DI, módulos, guards y pipes. Estructura limpia para una API con auth, validación y lógica de negocio.
Auth JWT + Passport + bcrypt Auth stateless, cada KAM recibe un token firmado. Bcrypt para hash de passwords. Guard protege todos los endpoints excepto login y health.
ORM Prisma 5 Type-safe queries, migraciones declarativas, cliente generado. Simplifica el manejo de Decimal y relaciones.
DB PostgreSQL ACID, soporte nativo para Decimal(14,2), enums, índices compuestos. Addon nativo de Railway.
Deploy Railway + Vercel Railway: deploy desde GitHub con Dockerfile, PostgreSQL addon integrado. Vercel: zero-config para Next.js, preview deploys automáticos.
Lenguaje TypeScript end-to-end Tipos compartidos entre frontend y backend. Reduce errores en runtime, mejora DX y refactorizabilidad.

Decisiones de stack notables

Auth custom vs NextAuth

Se empezó con NextAuth pero se migró a JWT custom para que cada KAM solo vea sus empresas. NextAuth agrega complejidad innecesaria cuando la auth es un POST simple con bcrypt + JWT.

Señales on-read vs stored

Las métricas (churn risk, expansion, priority) se calculan en cada request, no se almacenan. Evita stale data y simplifica el modelo. Aceptable para <100 empresas por KAM.

03Modelo de Datos

Índices

  • Company.kamId — Filtrar cartera por KAM (query principal)
  • Operation.(companyId, date) — Ordenar operaciones por fecha para cálculo de señales
  • Interaction.(companyId, date) — Timeline ordenado cronológicamente
  • Kam.email — unique, lookup en login y JWT validation
  • Company.taxId — unique, integridad de datos

Nota sobre campos reservados

El schema incluye campos preparados para Part 2 (healthScore, aiSummary, recommendedActions, aiGeneratedAt) que actualmente no se usan — las señales se calculan on-read via el Signals Engine.

04Decisiones de Producto

Qué mostramos y por qué

📊
Dashboard con KPIs arriba + tabla abajo

Los KAMs necesitan visión rápida de su cartera. 4 KPIs (total empresas, volumen 90d, en riesgo, oportunidades) dan contexto inmediato sin scroll. La tabla debajo permite drill-down.

⚡
Señales determinísticas calculadas on-read

Churn risk, expansion y priority se calculan con reglas explícitas basadas en actividad real (días sin operar, tendencia de volumen, mora, SOW, utilización de línea). No hay ML, lo que hace las señales auditables y predecibles para un evaluador técnico.

🤖
AI Summary generado por reglas

El "análisis inteligente" en el detalle de empresa usa template strings condicionales basados en las señales. Simula lo que haría un LLM pero es determinístico, sin costos de API y sin latencia extra. Preparado para reemplazarse por GPT/Claude en Part 2.

🔒
Aislamiento por KAM con JWT

Cada request incluye el token JWT. El backend extrae el kamId y filtra todas las queries. Un KAM nunca ve empresas de otro. Esto es core para el caso de uso — un CRM sin aislamiento no sirve.

📈
Gráfico de volumen financiado (12 meses)

En el detalle de empresa, un AreaChart muestra la evolución mensual del volumen financiado. Permite ver tendencias de crecimiento o caída que las métricas numéricas solas no comunican bien.

📝
Notas + timeline de interacciones

El KAM puede editar notas y ver el historial de contactos (WhatsApp, call, email, meeting) con resúmenes. Esto es el mínimo para que el CRM sea actionable, no solo un dashboard de lectura.

🎨
Diseño premium CSS-first

En vez de usar Mantine como diseño completo, se usó CSS custom inspirado en Stripe/Linear/Mercury. Bordea los 0-gradientes, spacing generoso, tipografía Inter con tracking tight. Da impresión de producto real, no de prototipo.

05Qué Dejamos Fuera y Por Qué

Feature Estado Razón
Resumen con LLM real Part 2 El "análisis inteligente" actual es determinístico (reglas). El schema ya tiene campos aiSummary y recommendedActions listos para integrar un LLM en Part 2.
CRUD de interacciones Deliberado El KAM puede ver el timeline pero no crear interacciones desde el CRM. Agregar un formulario con channel+summary era alcanzable, pero se priorizó el pulido visual y las señales.
Refresh token / token rotation Simplificado Tokens expiran en 8h. Para una prueba técnica, un access token en localStorage es suficiente. En producción se agregaría refresh token con httpOnly cookies.
Tests unitarios / e2e Fuera Se priorizó feature-completeness y calidad visual. El signals engine es el candidato ideal para tests unitarios (función pura) — pero el scope de Part 1 no lo requería.
Paginación Innecesario Con ~5-6 empresas por KAM en el seed, paginar no aporta. El modelo soporta take/skip en Prisma si escala.
Búsqueda / filtro por texto Deliberado Los filtros existentes (riesgo, expansión) y sort (prioridad, volumen, riesgo) cubren los casos de uso principales con 10 empresas. Full-text search sería premature.
Responsive mobile Parcial El layout usa CSS Grid y se adapta razonablemente, pero la tabla de empresas está optimizada para desktop. Un KAM trabajará desde su laptop.
Internacionalización Fuera Todo está en español (target: equipos KAM en CL/MX). i18n es overhead innecesario para el alcance.
Rate limiting / throttling Fuera Sería necesario en producción pero irrelevante con 2 usuarios demo.

Criterio de priorización

Se priorizó lo que demuestra criterio de producto sobre lo que demuestra completitud técnica. Un evaluador busca: ¿entiende el problema? ¿toma decisiones razonadas? ¿el resultado se ve profesional? Las features que quedaron fuera son las que no moverían la aguja en esas preguntas.

Lo que sí mueve la aguja
  • Señales de negocio bien diseñadas
  • Aislamiento de datos por KAM
  • UI pulida nivel producto real
  • Código limpio y refactorizado
Lo que no la mueve (en Part 1)
  • 100% test coverage sin features
  • Refresh tokens para 2 usuarios
  • Paginación con 10 registros
  • i18n sin usuarios internacionales
